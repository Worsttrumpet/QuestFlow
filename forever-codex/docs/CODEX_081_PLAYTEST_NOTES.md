# 0.8.1: the 0.8.0 dungeon playtest (Roy, level 23-24 Hunter, Wailing Caverns with a group of 4)

Client 1.60.1, build 70235. Overall behaviour felt good; one diagnostic error repeated three times.

## 1. OfferProbe: `OfferProbe.lua:119: attempt to index a secret string value (execution tainted by 'ForeverCodex')`
**Root cause (reproduced).** `OfferProbe.call()` keeps a short "sample of what came back" for the report: `tostring(v):sub(1, 60)`. For `UnitName("npc")` the client returned a **secret string**: a value this client will not let addon code read, compare, index, concatenate or do arithmetic on. `tostring()` of a secret is still secret, and `:sub` on it raised at line 119, inside the GOSSIP_SHOW handler, before anything was recorded (3 of 9 dialogs in the report). The code below it had the same problem (`pack[1] ~= ""`, `pack[1]:sub(1, 40)`, `guid:match(...)`, `e.title:sub(...)`), so fixing only line 119 would have moved the error.
**Which dialogs:** the report shows the 5 dialogs that did save were in cities; the 3 that failed were not saved, consistent with unit data being restricted in the instance. Whether the client secrets UnitName only inside instances, or in other restricted contexts, is NOT proven by this report.
**Fix.** Every value read from the client in OfferProbe goes through secret-safe readers (`text`, `num`, `isNil`, `sampleOf`): they ask `issecretvalue()` when the client has it and perform the real operation inside `pcall`. A value that cannot be read is treated as NOT GIVEN:
* an unreadable NPC name / GUID: the dialog is still recorded (`src = "CODEX_OBSERVED"`) but with NO npc identity (`npcUnreadable = true`, counted), so it supplies no per-NPC evidence; an empty list can never become "NOT_OFFERED" for an NPC Codex could not identify;
* an unreadable listing: new state `UNREADABLE`, distinct from EMPTY (no negative evidence) and LISTED (no positive evidence); an unreadable entry is left out and makes the listing INCOMPLETE; an unreadable quest id or title never becomes an offer;
* nothing is assumed about availability and nothing is promoted to AVAILABLE: only readable, listed quest ids are positive evidence, exactly as before. The provenance model (observed vs QuestieDB / static) is unchanged. No secret value is stored.
**Tests:** `tests/offerprobe_secret_tests.lua` (two simulations: a client with `issecretvalue()`, and one without it where the method call itself raises, reproducing the exact error; verified to fail on 0.8.0 with the same message at line 119).
**Not changed:** other modules read `UnitName("player")` and similar, which are not unit data of other players; they were not implicated. If the next report shows a secret error elsewhere, the same readers apply.

## 2. Instance / dungeon player position
**What the repo already knew:** `UnitPosition`, `C_Map.GetMapInfo` and `C_Map.GetWorldPosFromMapPos` exist on Forever (M3 / M8.10 probes). `IsInInstance` and `GetInstanceInfo` were NEVER probed: unproven. Nothing proves what any of them return inside an instance.
**What the two reports show.** The earlier report (not pasted here) read map nil / position unavailable inside Wailing Caverns. THIS report, in the same dungeon, read `map 1414 at 52.1, 55.1 | position available: true | world coords: true` and the planner measured 444 yd to a Barrens quest giver. 1414 is the Kalimdor continent map: the likeliest reading (UNVERIFIED) is that the client reports the instance ENTRANCE on the parent continent map, which is a real outdoor place but is not where the player is standing inside the dungeon. So the position is sometimes absent and sometimes the entrance, and neither is the player's physical location in the instance.
**What changed (smallest safe step).**
* `Context.instance` (feature-checked `IsInInstance` / `GetInstanceInfo`, every value read in `pcall`): `{ known, inInstance, kind, name, id }`. Unknown when the APIs are absent or fail; an unknown state is never treated as inside or outside.
* `Navigation.Assess` withholds the arrow and the waypoint ONLY when the client says the player is inside an instance (new reason `IN_INSTANCE`, said in words on the NOW card). An arrow computed from the entrance position while standing in a dungeon points nowhere useful.
* The report prints `Instance: IsInInstance ... -> ... | GetInstanceInfo ...` and a `position APIs:` line (which APIs exist, whether the map position and world coords answered, what `UnitPosition` returned by TYPE and its 4th value, never the coordinates). One dungeon report with the new build settles what Forever exposes there.
**What did NOT change:** the planner, candidate generation, sequencing, scoring and distances. Distances inside an instance are still measured from whatever position the client reports (the entrance, when it reports one). No dungeon navigation, no dungeon routes, nothing assumes the player wants dungeon content.
**Unsupported / unknown:** a reliable in-dungeon position (no API is proven to give one); `IsInInstance` / `GetInstanceInfo` behaviour on Forever; whether `UnitPosition` inside an instance is usable (the report will show its return types).

## 3. Quest tags
**Finding: nothing is broken; the report line was misleading.** `C_QuestLog.GetQuestTagInfo` was proven useful on Forever in 0.4.2 (`CODEX_REALCLIENT_FIXES.md` section 38: Elite = 1 on Rear Guard Patrol, Dungeon = 81 on The Power to Destroy, dungeon named "Ragefire Chasm" through `C_Map.GetAreaInfo`). In this report 0 of 5 logged quests came back tagged because none of Roy's five outdoor quests IS tagged; zero tagged says nothing about the API. The report line still said "unverified on Forever" and now says what is proven and that 0 is normal.
**Still unverified:** tags for quests that are NOT in the log (an Elite or dungeon pickup), and tag ids other than 1 and 81 (Raid, Heroic, ...).
**QuestieDB:** the bridge already reads `zoneOrSort` and `specialFlags`, but there is no evidence that either maps to the game's tag ids, and Questie itself derives tags from the same game API. Not used, not trustworthy as a tag source until verified against the real client. No quest-tag system was built.

## 4. Dungeon context feature (NOT implemented): what it would need
"You're in a dungeon, you have no dungeon quests ..." would need, reliably: (1) a proven `IsInInstance` / `GetInstanceInfo` (type party or raid, not pvp / arena), which the new report line will establish; (2) the game's dungeon tags on LOGGED quests (proven) to know whether any dungeon quest is active (`Dungeons.List`); (3) a non-empty outdoor plan (`plan.now` with an outdoor target), so there is something to return to; (4) group state, so a group run is never treated as a mistake; (5) a strictly quiet presentation: one dismissible info line, never NOW, never a notification, shown at most once per instance entry, and a setting to turn it off. It must never nag: farming, gear, helping friends and group runs are all legitimate. Until (1) is proven there is nothing safe to build.

## 0.8.1 real-client report (Roy, level 24, Hillsbrad Foothills; outdoors): what it confirms
* **No caught errors (0).** The OfferProbe error is gone outdoors. The secret-value path itself is NOT exercised by this report (no instance this time); it still needs a dungeon run. From 0.8.2 the report prints `unreadable (secret) values this save: NPC names or GUIDs N | whole lists N | API samples N` (0.8.1 stored the counters but did not print them).
* **Instance APIs exist on Forever:** `IsInInstance present -> false (type none)`, `GetInstanceInfo present -> name 'Eastern Kingdoms', id 0`, `UnitPosition present -> returns (number, number, number, number)`, 4th value `0`. Outdoors, `GetInstanceInfo` returns the CONTINENT name and map id (so its name is not an instance name unless `IsInInstance` is true), and `UnitPosition`'s 4th return is the continent / instance id (0 = Eastern Kingdoms). Inside an instance that value should be the instance's id; this is the first evidence that the position API gives an id that tells an instance from the open world. Still UNVERIFIED: its value inside a dungeon, and whether `UnitPosition` coordinates inside a dungeon are usable (they are instance-space and Codex has no geometry to use them against).
* **QUEST_GREETING fires on Forever** (first time seen): at Apothecary Lydon, `GetNumAvailableQuests` / `GetAvailableTitle` / `GetNumActiveQuests` / `GetActiveTitle` answered with titles and NO quest ids. It stays recorded-only (a title is not a quest id). The old comments saying it had never fired are corrected.
* **Quest tags:** `1 of 7 logged quests tagged`: `The Grave Knight` (Q:96986, a Forever-only id not in QuestieDB) came back as tag 81 Dungeon and drew the DUNGEON QUEST card, named by the quest log heading rather than the area-name API.
* **Skip fix holds:** Q:98298 is in the skipped list and is not in the plan (50 skipped quests, none recommended).
* **Warm-up:** `first scan spread over 68 frames, 483 ms of work`, first recompute 36.6 ms, 14 idle refreshes skipped in 57 s.
* **Unchanged / still open:** the trainer purchase hook shows 0 purchases this session (no evidence either way); `QUEST_DETAIL` 4 and `GOSSIP_SHOW` 13 fired with 3 quests of positive offer evidence.
