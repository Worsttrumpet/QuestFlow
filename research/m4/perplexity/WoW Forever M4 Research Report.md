# M4 Research Report: WoW Forever Data-Acquisition Pipeline

## Executive summary

M3 proved that a read-only addon can observe a real, usable subset of quest data — ID, title, level, objectives, XP, money, and NPC identity/coordinates — directly from live gameplay on Forever build 1.60.1.69977 (18 accepts, 23 turn-ins, 14 NPCs). It could not capture item rewards. This pass traces the reward-capture gap to a lifecycle/timing problem rather than an API-availability problem, confirms that prerequisite/chain data is structurally unobservable and must be inferred, and extracts a genuine confidence/deduplication model from QuestieLearner's actual source that is directly reusable for M4's design — while flagging a live P2P broadcast feature in that same addon that M4 should not copy. Nothing below is claimed to work in Forever unless M3 already demonstrated it; documentation and other addons' code are evidence about the API surface and about proven techniques, not about Forever behavior.

## What M3 established (all [V], user-provided)

Build 1.60.1.69913 (QuestV2 extraction) / 1.60.1.69977 (addon probe), product `wow_classic_beta`. QuestV2 gives a quest shell only. The addon observed, via normal APIs and lifecycle events: quest ID, title, level, objectives, XP, money, NPC name, NPC creature ID, NPC interaction coordinates. It captured XP/money from `QUEST_TURNED_IN` but not item rewards. A local `Cache/WDB/enUS/questcache.wdb` (signature `TSQW`, client version 69913) changed size/hash after quest activity but was not decoded.

## What M4 still needs to establish

Whether item/choice/spell/faction/currency rewards can be captured reliably and at what lifecycle moment; whether `questcache.wdb` needs decoding at all given the addon already supplies most of the row; how to represent quest-giver "active" vs "available" state; how to structure inferred prerequisite relationships without treating inference as observation; and a concrete, minimal-personal-data provenance schema for every assertion.

## API/reward research

This is the core M4 gap. Warcraft Wiki documentation ([2nd], undated version info on most reward pages) draws a distinction M3's probe likely missed: reward-item APIs read from "the currently viewed quest completion dialog," not the quest log.

- `GetQuestItemInfo(type, index)` with `type = "reward"|"choice"|"required"` returns name/texture/count/quality/itemID for "the current quest, i.e. the one for which the QUEST_* family of events has fired most recently" — a dialog-state API, not a quest-log query ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_GetQuestItemInfo)).
- `GetQuestLogRewardInfo` / `GetQuestLogChoiceInfo` called **without** a `questID` operate on "the currently viewed quest completion dialog"; called **with** a `questID` they read from the quest log instead ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_GetQuestLogRewardInfo), [Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_GetQuestLogChoiceInfo)).
- `GetNumQuestRewards` / `GetNumQuestChoices` give item/choice counts but the pages don't state required UI state at all ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_GetNumQuestRewards), [Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_GetNumQuestChoices)) — documentation gaps, not proof of no requirement.
- `QUEST_COMPLETE` fires "after the Continue button, immediately before Complete Quest" — i.e., the reward frame is populated and reward data should be readable, but the quest hasn't been turned in yet (added 1.0.0/1.13.2) ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/QUEST_COMPLETE)).
- `QUEST_TURNED_IN` payload is only `questID, xpReward, moneyReward` (added Patch 6.0.2/1.13.2) — this independently confirms why M3 got XP/money and nothing else from that event; the event was never documented to carry item data ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/QUEST_TURNED_IN)).
- `GetQuestReward(itemChoice)` "completes the quest and chooses a reward" — calling it commits the turn-in, so reward reads must happen *before* this call ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_GetQuestReward)).
- `C_QuestInfoSystem.GetQuestRewardSpells([questID])` returns `spellIDs[]`; no UI-state precondition is documented either way ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_C_QuestInfoSystem.GetQuestRewardSpells)).
- A legacy Wowpedia/Fandom mirror of the classic API list additionally names `GetQuestLogQuestText` (description + objectives), `GetQuestLogRewardMoney`, `GetNumQuestLogRewards`, and `GetRewardMoney` for the gossip-window reward view ([wow.fandom.com API list](https://wow.fandom.com/pl/wiki/World_of_Warcraft_API)) — this is old community documentation, useful only as evidence such named functions exist, not as proof of current signatures or Forever behavior.
- Reputation/faction and currency reward APIs (candidates: `GetQuestLogRewardFactionInfo`, a currency-count equivalent) could not be independently re-verified in this pass — their exact current signatures are **[?] unresolved**, not confirmed absent.
- Item names/icons may be genuinely uncached client-side: `GetItemInfo` can return `nil` for an item not yet cached locally, and `GET_ITEM_INFO_RECEIVED` fires once the server answers ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/GET_ITEM_INFO_RECEIVED)) — a second, independent reason item-reward capture can silently fail if read only once.

**M4 recommendation for the probe:** poll `GetNumQuestRewards`/`GetNumQuestChoices` + `GetQuestItemInfo("reward"/"choice", i)` at multiple points — on `QUEST_DETAIL`, immediately on `QUEST_COMPLETE`, and again after a short delay on `QUEST_COMPLETE` — all strictly before calling `GetQuestReward`. Retry item-name resolution on `GET_ITEM_INFO_RECEIVED` rather than assuming a single read succeeds. This is a testable hypothesis, not a proven Forever result — **[?]**.

## Quest giver/NPC research

M3's proven method (GOSSIP_SHOW → UnitGUID("npc") parsing) remains the only [V] technique. Two related gossip APIs exist that M3 didn't use: `C_GossipInfo.GetAvailableQuests()` (quests offered, not yet in log; exposes `questID`, `isComplete`, `frequency`, returns structured data as of Patch 9.0.1) and `C_GossipInfo.GetActiveQuests()`/`GetGossipActiveQuests` (quests "which can be turned in at a quest giver"; same field set) ([Warcraft Wiki: GetAvailableQuests](https://warcraft.wiki.gg/wiki/API_C_GossipInfo.GetAvailableQuests), [Warcraft Wiki: GetActiveQuests](https://warcraft.wiki.gg/wiki/API_C_GossipInfo.GetActiveQuests)). Neither page documents Classic/Era availability, so Forever support is **[?]**. Direct inspection of QuestieLearner's actual source confirms it does not call either gossip function; it captures `UnitGUID`/`UnitName` on `GOSSIP_SHOW` and associates the resulting entity with whatever quest is next accepted, because `GOSSIP_CLOSED` fires before `QUEST_ACCEPTED` ([Xurkon/Questie-X, Modules/QuestieLearner.lua, main branch as fetched](https://raw.githubusercontent.com/Xurkon/Questie-X/main/Modules/QuestieLearner.lua)). This is source-code evidence of a working technique in a related client family, not proof it works identically in Forever.

## Quest chain/prerequisite research

Nothing in the documented API surface returns a "requires quest X" or "leads to quest Y" relationship directly. `C_QuestLog.IsQuestFlaggedCompleted(questID)` only returns a boolean, and `false` can mean either "incomplete" or "invalid ID" — it cannot distinguish them ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_C_QuestLog.IsQuestFlaggedCompleted)). `GetQuestsCompleted()` returns quests only **after** they've been turned in — never while merely in the log — and some quests are invisible until another action marks them complete ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_GetQuestsCompleted)). `C_QuestLog.IsOnQuest(questID)` is a similar boolean flag ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_C_QuestLog.IsOnQuest)).

**Directly observable:** a quest's own completion/active state at a point in time; that quest B newly appeared at a gossip NPC in a session where quest A was turned in moments before. **Must be inferred, never asserted as fact from a single observation:** prerequisite chains, mutually exclusive branches, class/race/level/reputation/attunement gates. These require repeated observations across many characters and builds before even a probabilistic claim is warranted, and should be stored as `DerivedData` with a confidence value and a list of supporting `PlayerObservation` records — never promoted to a fact table.

## Player-observation architecture research

QuestieLearner's live source is the most useful precedent found. It implements a genuine confidence/dedup model, not just an event log: each NPC's learned entry stores a `guidSpawns` table keyed by `spawnUID`, where each entry is `{zoneId, x, y, ts, source, confidence}`; repeat sightings at the same spawn UID run a running-average position correction (`healedX = (oldX*count + newX) / (count+1)`) rather than overwriting; storage per NPC per zone is capped (8 entries) with oldest-eviction; and a `minConfidencePins` threshold gates whether learned data is exposed at all ([Xurkon/Questie-X, Modules/QuestieLearner.lua](https://raw.githubusercontent.com/Xurkon/Questie-X/main/Modules/QuestieLearner.lua)). This directly validates the M1 append-only/competing-observations philosophy: position healing is a form of "competing observations reconciled by confidence," not silent overwrite.

The same addon has a legitimate export path — `QuestieLearnerExport.lua` serializes the learned-data bucket with AceSerializer, compresses with LibDeflate, and encodes to a printable string tagged with a format prefix/version ([Xurkon/Questie-X, Modules/QuestieLearnerExport.lua](https://raw.githubusercontent.com/Xurkon/Questie-X/main/Modules/QuestieLearnerExport.lua)) — a clean, inspectable, opt-in pattern worth reusing. It also has a **separate**, more concerning feature: `QuestieLearnerComms.lua` auto-joins a hidden chat channel (`"questiecomm"`) and broadcasts learned data live via `SendChatMessage`, with the sender's `UnitName` visible to filter out one's own messages ([Xurkon/Questie-X, Modules/Network/QuestieLearnerComms.lua](https://raw.githubusercontent.com/Xurkon/Questie-X/main/Modules/Network/QuestieLearnerComms.lua)). This is automatic P2P sync, not opt-in export, and exposes character identity to other players by construction — **M4 should not replicate this pattern.** AllTheThings, by contrast, stores everything in plain per-character and account-wide `SavedVariables` files that the user can inspect or delete manually ([wowaddons.net](https://wowaddons.net/addon/all-the-things/)) — a simpler, more transparent model for a first M4 iteration.

## Cache/WDB research

M3's `questcache.wdb` (signature `TSQW`) sighting is [V] but undecoded. Given that the addon-observation path already supplies quest ID/title/level/objectives/XP/money/giver-identity/coordinates, and the open question is specifically item rewards — a field the WDB cache is not confirmed to expose either — **decoding the cache is not necessary to close M4's actual gap.** Recommendation: retain the cache only as passive corroborating evidence (header metadata, hash-before/after) exactly as M3 did, and do not invest in a parser until the addon-based reward experiment is exhausted.

## Build/provenance recommendations

Necessary on every assertion: client build, product/branch, addon version, probe/script version, UTC timestamp, source event/API name, and locale. Useful but optional: character level and class/race (only when the observed fact plausibly depends on them, e.g., a class-restricted quest), zone/map ID. Should NOT be retained: account name, real character name (a per-character opaque/rotating pseudonym or hash is preferable to omitting context entirely), realm/server identity beyond what's needed to prevent cross-realm quest-ID collisions, and any chat/social identifiers. This mirrors the QuestieLearnerComms problem above — identity fields should never be broadcast or embedded in exported strings by default.

## Blizzard policy/licensing considerations

The current official UI Add-On Development Policy, fetched directly, lists eight rules: free distribution, fully visible/unobfuscated code, no negative realm impact, no advertising, no in-game donation requests, ESRB-compliant content, mandatory ToU/EULA compliance, and Blizzard's right to disable add-on functionality at its discretion ([Blizzard official forum policy page](https://us.forums.blizzard.com/en/wow/t/ui-add-on-development-policy/24534)). None of the eight rules explicitly addresses data collection, export, or external communication by an addon — this is a genuine gap in the policy text itself, not an oversight in this research. Separately, 2025 reporting confirms Blizzard is actively narrowing addon API access for **combat**-related functionality specifically ([PCGamer](https://www.pcgamer.com/games/world-of-warcraft/as-world-of-warcraft-winds-down-its-combat-addon-support-director-ion-hazzikostas-is-all-composure-about-rule-breakers-because-frankly-this-is-far-from-the-first-time/)) and has also loosened some other API restrictions ([Wowhead](https://www.wowhead.com/news/blizzard-continues-to-loosen-addon-api-restrictions-and-whitelist-select-spells-379691)) — evidence that addon API policy is actively evolving, though neither source addresses quest-data collection specifically. This pass could not re-fetch the EULA page directly (fetch failed); any anti-mining/EULA claim should be treated as carried over from the prior M2/M3 report and re-verified before M4, not restated as newly confirmed here. Beta/test-client-specific terms remain **[?] unresolved** — no official beta agreement text was retrieved in this pass. Conservative engineering conclusion: build a minimal-footprint, fully visible, opt-in-export addon that never auto-transmits data over chat channels, and treat "not explicitly prohibited" as distinct from "affirmatively permitted."

## Recommended M4 data-acquisition contract

Every observation record should carry: `source_kind` (addon-event / cache-header / doc-citation), `build`, `product`, `addon_version`, `probe_version`, `event_or_api`, `timestamp_utc`, `locale`, an optional minimized character context (level/class only if relevant, no name/account/realm by default), and a `confidence`/`status` field consistent with the M1 architecture. Reward fields should record which lifecycle moment produced them (`QUEST_DETAIL`, `QUEST_COMPLETE-immediate`, `QUEST_COMPLETE-delayed`) so later analysis can tell which timing actually worked in Forever. The `ClientData → PlayerObservation → DerivedData → ExternalCorroboration` separation the user proposed is sound and matches what QuestieLearner effectively does in practice (raw sightings vs. healed/confidence-gated learned entries vs. curated `AscensionDB`/`QuestieDB` overrides it merges against) — keep `ExternalCorroboration` strictly comparison-only, never auto-merged into `PlayerObservation`.

## Open questions requiring real-client testing

Which exact moment(s) let `GetQuestItemInfo`/`GetQuestLogRewardInfo`/`GetQuestLogChoiceInfo` return non-empty item data in Forever specifically; whether `C_GossipInfo.GetAvailableQuests`/`GetActiveQuests` work in Forever at all (Classic/Era availability undocumented); whether reputation/faction and currency reward APIs exist and work in Forever (unresolved even in general documentation); whether `questcache.wdb`'s changed hash reflects quest reward data or only log-state metadata; whether `GetQuestsCompleted` reliably distinguishes real prerequisite gating from coincidental quest-list changes.

## Recommended M4 experiments

1. **Reward-timing probe**: extend the M3 addon to call the reward-query APIs at three checkpoints (`QUEST_DETAIL`, `QUEST_COMPLETE` immediate, `QUEST_COMPLETE`+short delay) across a batch of quests with known item rewards, logging which checkpoint yields non-nil item name/ID/count, all before ever calling `GetQuestReward`.
2. **Gossip active/available probe**: call both `C_GossipInfo.GetAvailableQuests()` and `GetActiveQuests()` at every `GOSSIP_SHOW` and log raw return tables to establish whether they function at all in Forever, independent of the already-proven `GOSSIP_SHOW`+`UnitGUID` method.
3. **Prerequisite-inference probe**: log the full gossip-offered quest list at an NPC before and after turning in a specific quest, across multiple sessions, to build the first small evidence set for inferred (not asserted) prerequisite relationships.
4. **Item-cache retry probe**: verify whether `GetItemInfo` returns nil for reward items on first read and whether `GET_ITEM_INFO_RECEIVED` reliably fills it in on retry, within the same reward-capture window as experiment 1.
